# Client-side project access

The 0.12.81 GitHub preview contains the earlier session-loading work. The strict foreground-only transport and optional inline viewer described below are development changes after that preview; store approval and installed-browser acceptance are separate.

## Viewing

Click the extension on an open GitHub or approved GitLab project tab. The extension installs a small read-only bridge in that tab's isolated world using temporary activeTab access. By default it opens its own viewer tab. Settings → Project opening can instead select an in-page viewer, with Close and Open in tab controls. The manifest has no permanent repository host permissions or automatic page content scripts. Only four viewer entry pages are web-accessible for the optional embedded frame; worker reads require an extension-owned frame bound to the clicked repository. Website CSP or managed-browser rules can prevent embedding; use Open in tab in that case. Self-hosted GitLab configuration records an approved HTTPS origin without requesting a standing viewing grant; obsolete persistent content registrations are retired.

All supported project resource loading—including schematics, PCB files, hierarchy, project settings, saved analysis/rule reports, PDFs and component models—uses the content transport independently of review-account tokens. Resources load as needed within the existing file, traversal and memory limits; this is not an unlimited download of every repository object.

GitHub uses website metadata and raw downloads, with no REST/GraphQL calls for ordinary project viewing. Private repository/folder context is resolved in the matching signed-in website tab first, including slash-containing branch names, then pinned to a commit. Production project viewing never falls back to a background network request. A missing website session returns guidance to reopen the repository in the same signed-in profile and click the icon again. Validated text and model bytes use a bounded worker-memory cache, keyed by repository, immutable revision and path, for up to 30 minutes and 128 MiB total. This cache is temporary and is lost when the worker is stopped. No cookies or tokens are stored in it. Session storage retains only the clicked tab and repository binding so a restarted worker can find that tab without a broad tabs grant.

GitLab uses same-origin website-cookie requests to its read-only `/api/v4` endpoints through the clicked website tab, with no background content fallback. This is token-free content loading, not API-free GitLab viewing. The content adapter never asks the review connector for Authorization or PRIVATE-TOKEN headers. Self-hosted server versions and proxy/SSO arrangements may affect website-session API availability.

SSO/SAML, login requirements and administrator restrictions are respected. The extension cannot open files that the website session or organization policy forbids. Keep the chosen repository tab open; after navigation, closing it or losing temporary site access, reopen it and click the icon again. Local selected files/folders remain the fallback where permitted.

## Organizations that do not authorize third-party apps

Organization approval for an OAuth/GitHub App is separate from the employee's normal website access. For viewing, leave the extension's review account disconnected, open the repository in the signed-in Chrome/Firefox profile, and click the extension icon. The on-demand reader uses that specific website tab; it does not request organization-wide repository access or send project files to a viewer backend. Temporary `activeTab` access is still real permission to read the clicked page, not permission-free access.

If browser policy blocks the extension itself or its page access, it cannot override that policy. Where the organization permits downloading the design, use the repository website's **Code → Download ZIP** (GitHub) or **Download source code** (GitLab), extract the archive, then choose **Open downloaded project folder** in the error view. Select the project folder to include relative subsheets and model files. This uses the existing local file/folder viewer and does not require a provider token, native helper or a backend upload. If downloads are also prohibited, an administrator-approved workflow is required.

## Reviews and remote actions

Connecting an account is optional for viewing. Optional persistent provider-site grants are requested only by explicit account-connect/token-save controls for commenting and connected review actions. Existing remote mutation features, such as saving Draftsman output or creating a fork, still require explicit authorization and are not implied by loading source files.

The extension's comment composer also offers **Continue on GitHub/GitLab website…** in its `+` menu. This saves a local draft and prepares complete Markdown, including the sheet/object/point or area metadata. Copy it and open the provider's normal website composer; a short new issue can be prefilled. Existing issue/discussion replies use an explicit website link and copy/paste. This manual handoff does not mark the local draft published. Screenshots and attachments need manual upload there. Local drafts remain usable without a connected review account.

### Development beta: GitHub website-session Issue conversations

Drawing annotations read back from GitHub retain their saved repository, revision, filename, sheet identity, millimetre position and optional rectangular area. The matching schematic or layout shows numbered markers and severity-coloured areas; the 3D PCB view projects PCB annotations onto the saved board side. Selecting a marker opens its linked conversation. Areas follow the camera, including rotation. Schematic coordinates are not treated as PCB coordinates, and ordinary messages without drawing metadata remain in the conversation without an invented marker.

Without a selected Issue, the website-session reader scans up to eight Issues from the current website listing, caches that scan for 30 seconds and the listing for 60 seconds, and shows incomplete-coverage warnings. Open a particular Issue for its full available snapshot. Selected conversations use the existing foreground refresh loop. Incomplete snapshots retain previously read markers; complete selected-thread readback removes deleted annotations. This is bounded polling rather than a webhook or guaranteed real-time feed.

The local development build adds a separate browser-session transport for existing GitHub Issues. Invoke the extension on the signed-in repository tab. In Comments, open an Issue conversation, or choose **Conversation list options → Browser-session conversation** and enter its number. The repository's Issue page must remain open for direct Send. No OAuth token, cookie-reading permission or persistent repository host grant is added. This beta does not bypass repository permissions, SSO, administrator controls or provider challenges.

Reads fetch the ordinary Issue website page in that repository's isolated content-script context, extract bounded raw Markdown and provenance from its issue snapshot, and preserve drawing annotation markers. Visible conversations refresh without reloading the viewer; concurrent reads share a ten-second snapshot. The dedicated conversation page polls every fifteen seconds, backs off on errors and pauses while hidden. This is foreground polling, not push delivery or guaranteed instantaneous synchronization.

An explicit Send prepares GitHub's existing rendered comment composer. GitHub retains responsibility for session and CSRF submission; the extension does not extract or export credentials or construct a private GraphQL mutation. A short-lived, one-use preparation ticket is bound to the repository, Issue, website account and exact draft. A fresh server-side actor/permission check precedes a final administrator-policy check and commit. Existing website drafts are preserved. A durable pending receipt is written before the single click; uncertain outcomes cannot automatically resend. Readback confirms a new matching comment ID, and a later exact marker match can recover its receipt without another write.

The beta supports reading existing Issues and sending text or validated drawing-context replies. New Issues, Discussions, edits, state changes and screenshot uploads are not supported by this website adapter; their existing website handoff or explicitly connected provider workflow remains separate. Website markup can change and the adapter fails closed when it cannot identify the exact composer or account. Installed-browser readback of an authorized organization QA Issue passed with the review account signed out; direct Send and external-to-viewer update acceptance remain pending until the live test completes. Do not treat unit tests as proof of live posting.

GitHub/GitLab legacy OAuth scopes can themselves be broader than comments; a client cannot redefine provider scopes. The UI discloses GitHub private `repo` scope. For least privilege, use provider-supported fine-grained credentials or a selected-repository GitHub App with only the needed review permissions. This change isolates token use from content loading; it does not claim that legacy OAuth has become issue-only. Existing installed optional grants/authorizations may remain until the user revokes them.

## Security and acceptance

The bridge accepts only messages from this extension's non-tab contexts, and the readers validate exact website origin, repository namespace, safe paths and pinned identity. It never serializes cookies or signed raw URLs. Concurrent reads are limited to 4 and 128 MiB of reserved response budgets; individual source reads are capped at 64 MiB and binary assets at 32 MiB. Text responses do not accept login HTML as CAD source. Known SSO error codes use static messages; arbitrary provider error payloads are not forwarded.

Tests cover foreground-only flows with background project fetches and review-token access configured to throw, nested namespaces/slash branches, cancellation, limits, foreign-origin/project rejection, opt-in permissions, message provenance and comment/content transport separation.

## Compatibility and permissions

| Situation | Viewing access | Acceptance evidence |
| --- | --- | --- |
| Public GitHub repository, nested project folder or pinned commit | Click the extension on that repository tab; no review login | Transport and discovery regressions with real public path inventories |
| Private GitHub repository | The normal signed-in website session, with the repository tab kept open | Installed Chrome opened a user-authorized private ESP32-PoE M2 copy and linked real models to 126 of 143 components; the review account was signed out |
| GitHub organization repository | Existing website membership and any required SSO; temporary access on the clicked tab | Origin/identity/SSO/policy failure cases tested; no live managed-organization acceptance yet |
| GitLab.com or configured self-hosted GitLab | Same-origin website session for read-only content API endpoints | Private session, nested namespace, permission revocation and authentication-page tests; live private GitLab acceptance pending |
| Administrator blocks extension installation, injection, downloads or the repository website | Administrator must permit the operation; use locally selected files where policy allows | Denial handling tested; the extension does not bypass policy |
| GitHub Enterprise Server on a custom domain | Not currently supported by the GitHub adapter | Do not grant a broad account token as a workaround |

Viewing does not require a GitHub OAuth `repo` grant, GitLab API token, organization-owner role, administrator role, cookie-reading permission or access to every repository in an account. Temporary `activeTab` access still lets the extension read the clicked website tab: this is real access and should not be described as zero permissions. Existing organization rules may require IT approval to install any extension. Existing grants from older installed versions can remain until revoked; the new manifest does not silently revoke permissions needed by an already-connected review workflow.

### Opening projects and models

Open the actual repository or project folder in the normal signed-in browser, then invoke the extension icon. The viewer opens separately. Keep that source tab open so the isolated reader can retrieve private files with its existing session; it does not export cookies or credentials. After restoring a viewer tab, reloading the extension or switching browser profiles, open the repository in that same signed-in profile and click the extension icon again to establish temporary website access. An optional review-account sign-in is separate. GitHub can return HTTP 404 for missing website/SSO access as well as a missing revision; explicit access errors are retained rather than retried anonymously. Complete SSO on the provider website itself when required.

The reader supports both embedded GitHub tree JSON and the server-rendered file table. For a nested folder on a mutable branch, it resolves that branch's root commit before reading the folder at the immutable revision. A folder's last-change commit is never treated as branch HEAD. Model discovery begins beside the selected PCB and adjacent shared model folders, with an independent bounded inventory; incomplete unrelated historical folders cannot erase a complete board model index.

Model files must actually be present in the repository or embedded in the board. The browser cannot read an author's local KiCad library directory. Unavailable or ambiguous references remain visible diagnostics; the loader does not substitute a different component merely to increase the linked count. In the M2 test, unavailable library references remain among the unlinked components.

### Development verification (2026-11-03)

The foreground-only development build passed 2,300 JavaScript checks and 24 affected packaging/metadata checks before the subsequent website-comment handoff changes. The retained `client-session-checks/foreground-current-js.log` and `foreground-current-python.log` in the main D: checkout record that run. A broader Python run had one Windows socket-abort error in its chunked-webhook fixture and two skips; it was not an all-green full gate.

Installed Chrome opened the private M2 test project from the icon-created chooser with the review account signed out. The schematic and PCB canvases rendered; 3D linked real models to 126 of 143 components. Missing library references and saved-geometry limitations remain visible diagnostics, so this does not establish complete 3D fidelity. Discovery explicitly disclosed its partial listing. Installed Firefox acceptance remains unverified.

On 2026-11-04, the local development build also opened an authorized organization-managed repository from its root-page icon with the review account signed out. Its project metadata, root schematic and PCB layout rendered through the foreground website session. A literal `#` in a repository STEP filename had previously aborted all discovery. The snapshot validator and model resolver now accept this filename character; transport URLs still encode each segment as path data, and traversal, encoded-path ambiguity and unrelated redirects remain rejected. This is a focused check of one authorized organization profile, not a claim that administrator policies or inaccessible repositories can be bypassed. The scan disclosed its partial inventory; complete model coverage remains a separate verification requirement.

The same check rendered the 3D board but linked no real component models. Diagnostics included network-drive references, unavailable repository assets and website-read failures. Company network paths remain blocked. Follow-up changes narrow root-board model discovery to recognized model folders, retain literal `#` through viewer asset dispatch, and accept asset redirects only to GitHub's exact repository/commit/path on its LFS media host. These passed focused tests and independent security review, but their installed-browser model-loading retry remains pending because desktop control stalled. CORS or organization policy failures cannot be fixed by this redirect rule, and broader OAuth permissions are not the fallback.

Repository landing pages and ordinary file/PR browsing remain untouched by default: no automatic content scripts are declared. An inline viewer appears only through the explicit opening preference/action. A page that retained an older version's injected UI may need a normal page refresh to discard that old document; updating the extension does not grant permission to rewrite every existing tab.

Development archives and local-only private test screenshots are retained under `.vizdiff/client-session-checks/` in the main D: checkout. Private test materials are not included in public documentation or release packages. Published release artifacts were not changed.
