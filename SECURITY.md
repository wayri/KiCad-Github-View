# Security reporting

Do not post access tokens, private repository files, OAuth credentials or private keys in public issues. Use GitHub's private vulnerability reporting when the repository owner enables it, or contact the owner privately through their published contact channel.

Reports should identify the affected version, viewer surface, reproduction steps and whether the issue crosses the isolated HTML, extension worker, repository scope or VS Code message boundary. Use a minimal synthetic example where possible.

## Current assessment

The [27 October 2026 assessment](docs/SECURITY-AUDIT-2026-10-27.md) records source fixes, verification and restrictions for controlled deployment. The 0.12.63 / Android 1.65 security update incorporates those corrections; [deployment profiles](docs/HARDENED-DEPLOYMENT.md) describe additional managed controls and remaining operational requirements. This project does not claim high-security certification.

## Authentication protection

Browser packages encrypt GitHub and per-server GitLab tokens using AES-256-GCM before writing them to extension session storage. Each save uses a fresh key and random 96-bit IV. Expiry metadata is authenticated; changed ciphertext, IVs or expiry fail closed. Non-extractable keys exist only in memory and are never stored alongside ciphertext, exported, synced or written into review files. In Chrome with the required offscreen and service-worker messaging APIs, a dedicated worker in an offscreen document retains the keys independently of the background service worker. Its authenticated data also binds each record to its provider and GitLab server. Unsupported browsers retain keys only in the background process. Startup removes obsolete plaintext and records without usable keys. Pending OAuth device secrets stay in background memory and do not survive its restart.

Sessions last at most eight hours, or the shorter expiry returned by the provider. Supported Chrome sessions retain their encrypted credentials through ordinary background service-worker suspension and restart. Browser restart, extension reload or loss of the offscreen key worker requires sign-in again. Browsers using the fallback also require sign-in after background-process restart. The key worker enforces expiry and serializes credential changes with clearing. Sign-out destroys the key, deletes credential records and cancels pending login. **Reset GitHub connection** additionally removes the custom public OAuth client ID while preserving review notes. Late login responses cannot restore a signed-out session. This implementation uses Chrome's [offscreen worker support](https://developer.chrome.com/docs/extensions/reference/api/offscreen); it does not send keepalive traffic to prevent background suspension.

Host page scripts cannot request raw credentials, and only the exact extension settings page can set, clear, reset or initiate authentication. The offscreen vault uses a private MessageChannel addressed to its exact document; the document accepts a channel only from the extension's background service worker. Vault files are not web-accessible resources. Settings still submit manually entered tokens through extension runtime messages, so other privileged extension frames remain within the trust boundary. Authenticated GitHub requests go to `https://api.github.com`, or to the fixed `https://uploads.github.com/user-attachments/assets` endpoint when the user publishes a captured PNG. Redirects are rejected. Public raw-content fallbacks never receive tokens. No OAuth client secret or refresh token is retained.

Screenshot publication uploads the selected drawing area to GitHub as a repository attachment. Images may contain private design information: review the preview and destination before choosing Post. Upload requires repository write access and an OAuth or personal access token; GitHub App tokens and GitHub Enterprise Server are unsupported by this upload path. Captures have bounded decoded size and PNG header dimensions, and returned URLs must be exact GitHub UUID attachment URLs. Failed uploads stop publication. GitHub controls attachment access and retention; sign-out or deleting a local annotation does not delete an uploaded asset. An upload followed by a failed post can leave an unreferenced asset. Confirmed assets are reused on a retry with the same repository, note and image.

Encryption protects copied ciphertext without its memory-resident key; it does **not** make a decrypted bearer token non-replayable or guarantee that an attacker with control of a usable browser profile cannot obtain it. Malicious code running inside the extension, a compromised browser/OS, privileged debugging, or process-memory capture can access credentials during use. JavaScript does not offer guaranteed zeroization of immutable strings. A request already sent before sign-out cannot be recalled.

Removing the extension clears its browser storage under the browser's extension lifecycle. There is no reliable uninstall callback that can revoke GitHub authorization. Local deletion does not invalidate a stolen plaintext token or remove the account's GitHub authorization. Revoke OAuth access in [GitHub application settings](https://github.com/settings/applications), or a manual PAT in [token settings](https://github.com/settings/tokens). See [Chrome storage lifecycle](https://developer.chrome.com/docs/extensions/reference/api/storage), [Firefox session storage](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/storage/session), and [GitHub token revocation](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/token-expiration-and-revocation).

Use narrowly scoped, expiring credentials and repository permissions. The current OAuth `repo` scope is broad; encryption does not narrow it. GitLab OAuth requests the broad `api` scope; use expiring read-only credentials when only private viewing is needed. VS Code remote token publication is not implemented. Automated tests exercise real WebCrypto, corruption rejection, expiry, simulated background recreation with a retained key worker, key-worker loss, cleanup races, sender restrictions and provider isolation. Actual Chrome idle suspension, offscreen lifecycle and browser-restart behavior have not yet been verified in an installed browser. Safari also requires real macOS lifecycle verification. These checks do not establish live OAuth acceptance.

Repository HTML previews run separately from privileged viewer documents. Design files are read-only; review annotations can be stored locally or explicitly published. See the extension documentation for current isolation and compatibility limits.

## GitLab server isolation

GitLab credentials are bound to one normalized HTTPS origin. Additional servers require an explicit browser permission grant in **GitLab accounts and servers**; adding a server registers its inline preview scripts. Requests attach that server's credential only to its own API and reject redirects. GitHub tokens are never sent to GitLab. Review notes, read receipts and remote references preserve both provider and server identity. A host page cannot change authentication or invoke issue publication; those actions are restricted to extension settings/viewer pages.

GitLab sign-in uses OAuth authorization code flow with PKCE and random state. Register a non-confidential application with the exact browser-provided redirect URI and public Application ID. No client secret or refresh token is stored, and there is no bundled GitLab Application ID. Sign-out/reset delete the server's encrypted credentials and invalidate pending login; reset also deletes its custom Application ID. Removing a server additionally unregisters its preview and removes its browser permission. Review notes remain intact. Safari may lack the required browser identity API; the encrypted token connection is the fallback.

Uninstall removes local extension data but cannot revoke remote GitLab access. Revoke tokens and OAuth grants separately in the selected server's account settings. Encryption does not protect plaintext already stolen from a compromised running browser. Contributor commit emails do not prove GitLab account authorship: the GitLab contributors-only policy fails closed without verifiable account membership or an explicit allowlist. Use collaborator or allowlist policy for predictable access. Policies govern the extension's posting workflow; GitLab permissions still decide API access, and users may post directly through GitLab.
